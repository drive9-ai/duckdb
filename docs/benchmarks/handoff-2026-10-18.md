# Native DuckDB handoff benchmark — 2026-10-18

This measures a clean, exclusive-writer handoff of an actual multi-GiB DuckDB
database over the existing extent APIs. It separates outgoing flush/close,
incoming process/plugin bootstrap, ATTACH/reopen, and the first full scan.
It is a preliminary single-host experiment, not a production or WAN benchmark.

## Test environment

- Apple M4, 10 CPU cores, 24 GiB RAM, macOS 27.0.1 arm64.
- DuckDB 1.4.2; four query threads; `memory_limit='6GB'`.
- Benchmark controller: Python 3.9.6, boto3 1.42.97, PyMySQL 1.1.2.
- Current plugin source `973313c2775fb7667a5aee9e6f2dc35d177b95b3`, rebuilt for this run.
- TiDB File System server built from `f21d5acde9b1a3cb97935e3447671a31227f22af`.
  This server checkout is private; the binary SHA-256 is recorded in the raw results.
- TiDB 8.5.3 in unistore mode, RustFS 1.0.3 implementing S3, and all worker
  processes on the same Mac using loopback HTTP/TCP and local APFS storage.
- Direct FS-client-to-S3 block reads/writes; no Python data proxy or FUSE mount.
- Disposable static S3 test credentials; external STS/IAM credential-mint
  latency is not included. Production credential setup can differ.
- The existing 64 MiB in-memory extent read cache and sync-per-write policy
  are unchanged. The server's default logging remains enabled.
- No existing database, bucket, production credentials or service was used.

## Dataset and query

`samples` starts with 50,331,648 rows and eight 64-bit columns: one sequential
BIGINT ID and seven deterministic hashed UBIGINT values. Compression is forced
to `uncompressed`, giving 3 GiB of column payload before database block headers
and metadata. The actual checkpointed file length is recorded separately.

The measured query reads every column of the entire table; this is deliberately
more work than a metadata-only `count(*)` or a selective first query:

```sql
SELECT count(*), sum(id), sum(v1), sum(v2), sum(v3),
       sum(v4), sum(v5), sum(v6), sum(v7)
FROM samples;
```

Every scan validates the exact row count and all eight column sums against the
baseline plus independently computed appended values. Results are retained as
decimal strings, preserving 128-bit aggregate precision in JSON.

## Procedure and cache definitions

There are five trials in each cohort, in this order:

1. **Already checkpointed:** no new writes before handoff.
2. **Committed append:** each outgoing worker commits 131,072 additional rows,
   or 8 MiB of raw column values, with auto-checkpointing suppressed. The actual
   WAL length is measured; 8 MiB of appended values is not assumed to equal 8 MiB
   of WAL. These additions accumulate, so file size and expected row count are
   recorded for every trial.

Each trial starts a fresh outgoing writer too. Its earlier open and
cohort-specific work are outside handoff timing; it is not prewarmed by a full
scan. This outgoing-cache state is part of the workload definition.

Each outgoing worker explicitly runs `CHECKPOINT remote`, then
`USE memory; DETACH remote`, then exits. These three phases are timed separately;
their sum is reported as old-worker flush/close. The prior append/COMMIT time
is also retained separately rather than charged to the handoff.

A new OS process then loads the extension, configures its secret and settings,
and signals readiness. That process/plugin bootstrap is timed separately from
ATTACH. The measured reopen is `ATTACH ... AS remote; USE remote`, including its
credential/session setup, locking and catalog reads. It is not simply a local
file-open call.

- **Client-cold first scan:** the receiver is a fresh process. It inherits no
  DuckDB buffer pool or extent-client cache from the previous worker. Reopen has
  already loaded any metadata it needs before this scan begins.
- **Client-warm scan:** the same SQL is repeated twice in the same process and
  database connection, after the first scan. The database fits within the
  configured DuckDB memory budget. Each repetition is validated independently.
- **Backend/OS caches:** TiDB, RustFS and OS caches remain running and are not
  purged. Dataset preparation and prior scans may warm them. These numbers do
  not represent cold disks, a cold object service, or a cold production cluster.

Timers use Python `perf_counter` around CLI commands and a trailing SQL result
barrier, so they include small local command/acknowledgement overhead. CLI
startup is measured separately from reopen. The raw `flush_to_first_result_seconds`
field is a **derived sum of timed phases**, not an independently timed wall-clock
handoff; it excludes untimed size probes and orchestration gaps.

## Results

Completed 2026-10-18, 17:59–18:11 PDT. The initial physical database was
**3,437,244,416 bytes = 3.201 GiB**
(3.437 GB), using the uncompressed dataset described above.
Five handoffs per cohort and all 30 timed scans passed count/checksum validation.

| Phase | Already checkpointed | Committed append before checkpoint |
| --- | ---: | ---: |
| Old worker: CHECKPOINT | 0.231 ms (0.202–0.283) | 2364.227 ms (189.233–2444.093) |
| Old worker: DETACH + process exit | 6.265 ms (5.635–6.895) | 11.540 ms (9.242–13.718) |
| Old worker: total flush/close | 6.467 ms (5.848–7.178) | 2374.977 ms (202.950–2455.325) |
| New worker: process + plugin bootstrap | 19.605 ms (19.276–20.596) | 20.274 ms (19.516–20.810) |
| New worker: ATTACH/reopen | 27.516 ms (25.778–30.452) | 27.383 ms (20.982–32.287) |
| First full scan, client-cold | 26.726 s (26.198–26.774) | 27.026 s (26.843–28.234) |
| Repeated full scan, client-warm | 0.608 s (0.552–0.629) | 0.620 s (0.576–0.710) |

Cells show **median (minimum–maximum)**. Each first-scan column has five
samples; each warm-scan column has ten (two repeats per handoff). Times are
elapsed command times, not CPU time. No sample was discarded.

The earlier append/COMMIT, excluded from handoff timing, took
**0.920 s median (0.846–1.194 s)**.
The committed-append cohort's actual WAL was only **4,102–4,109 bytes**.
This is an 8 MiB bulk-append scenario, **not an 8 MiB WAL scenario**. It cannot
establish close/recovery costs for a large WAL. The first dirty checkpoint took
0.189 s, while the other four took 2.363–2.444 s; the table retains that variation.

The physical file grew to 3,507,236,864 bytes
(3.266 GiB) after five appends;
rows grew from 50,331,648 to 50,987,008. Queries and per-trial expectations reflect
these actual counts.

**Measured conclusion:** ATTACH/reopen was about 27 ms here, but a fresh worker's
first scan of all eight columns took about 27 s. Repeating the same scan in that
worker took about 0.6 s. A quick reopen does not remove the client-cache warmup
cost. Dirty-state checkpointing is a separate cost from reopen.

## Interpretation and boundaries

Handoff does not copy the database to the new worker. The worker reads shared
files on demand, so reopen and first-query performance answer different
questions. The scan here intentionally touches the full data working set;
selective queries can behave differently. Repeating a query is not a warm-cache
handoff to a different fresh process.

The extent read path does not provide a shared server-side data-block cache.
Shared TiDB metadata and potentially warm storage/OS caches do not transfer a
DuckDB buffer pool between workers.

These are clean handoffs after acknowledged writes, with one writer at a time.
They do not measure crash takeover, stale-session cleanup, large-WAL recovery,
network partitions, cross-machine cache locality, or public-cloud object latency.
Filesystem locks remain advisory, and the integration remains experimental.

## Reproduce

Build the extension against DuckDB 1.4.2. Provide compatible TiDB 8.5.3,
TiDB File System and RustFS binaries; all test services are started on private
loopback ports and cleaned up by the harness. Python needs `pymysql` and `boto3`.

```sh
python3 scripts/benchmark_handoff.py \
  --tidb-server /path/to/tidb-server \
  --fs-server /path/to/drive9-server \
  --rustfs-server /path/to/rustfs \
  --trials 5 --log-dir build/handoff-3gib

python3 scripts/summarize_handoff.py build/handoff-3gib/results.json
```

The harness defaults to 3 GiB raw payload and five handoffs per cohort. Smaller
`--rows`, `--dirty-rows` and `--trials` values are useful for checking setup, but
must not be presented as results for the full dataset.
